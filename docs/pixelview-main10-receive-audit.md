## Implementation follow-up: ordinary video routing simplified

The source implementation now supersedes the ordinary-video topology described below (the original audit remains historical evidence, not a current graph dump).

- `request-encoded-filter` remains because rswebrtc 0.15.2 supplies **downstream raw caps**, not the chosen encoded codec, to that signal. A supported CAPS-event pad probe selects the parsed codec. Main/Main10 use only a stock `capsfilter`; their compressed buffers no longer enter the native tap, native decoder, or its 3-buffer/16MiB/200ms queue. No compressed AU is rewritten, latest-replaced, or queue-dropped. Codec-family/profile renegotiation is refused by the pinned caps policy; a new receive attempt selects a new route.
- Explicit `main-422-10` inserts the existing native transform and raw-preview queue before the first AU. Its header/range/rate admission, native x422-to-v210 conversion and finite-rate timing are unchanged. The early ordered-RTP observer is still installed before HEVC depay to preserve native startup acquisition; after ordinary CAPS selection it removes its buffer probe on the next packet. Thus **not zero custom inspection**, and not a GStreamer fork or custom ordinary decoder.
- Ordinary decoded video goes `decodebin3 → P010 policy → clocked appsink → obs_source_output_video2`. The redundant external decoded-video queue was removed. Factory/rank selection remains GStreamer's decision. Limited Rec.709 validation, owned-sample mapping and conventional segment-running-time plus pipeline-base timestamps remain the OBS adapter.
- Only optional native422 preview uses the latest-sample worker. Pipeline teardown disables delivery, drains appsink callbacks with NULL state, then joins the native worker without receiver/delivery locks, clears OBS, and only then permits the next pipeline to start. Stop/connect procs remain invalidation-only. An externally blocked OBS callback can delay restart/destruction; it is never detached or allowed to overtake a new direct ordinary frame.
- Receive jitter/default/UI remain **100ms**. Profile advertisement, capability policy, native422 decoder implementation and feed ABI were not expanded or changed in this video work. Source audio graph/feed and rendered DeckLink audio changes are separately owned; this section does **not** claim their complete path is all-stock or removed.

## Actual source path

- `pixelview-whep.c:577–620`: `whepclientsrc` offers H265/H264/VP9 plus Opus, installs `request-encoded-filter` for every video codec, and sets/readbacks actual `webrtcbin.latency` in `webrtc_ready` (497–515). Frontend `OBSBasic_PixelviewReceive.inc` explicitly requests100; plugin connect fallback/default/create also100. This is not a per-profile setting or persisted private-source migration.
- Patched rswebrtc0.15.2 `src/webrtcsrc/imp.rs:713–784`: WebRTC RTP pad → parsebin (HEVC depay/parser) → encoded filter → decodebin3 → raw output. Main10 compressed caps do **not** enter native422 decoding: `native-422-filter.c:65–67,107` requires exact `video/x-h265,profile=main-422-10`, otherwise forwards the original buffer. However every ordinary video still crosses its nonleaky queue:3 buffers /16MiB /200ms (`:248–251`). Ordered-RTP observation is installed, but strict native admission/PTS/duration checks are below the `native_started` guard and must not be attributed to Main10.
- Decodebin3 selects by available factory/caps/rank, not an application-enforced decoder name. Read-only staged-runtime inspection returned `vtdec_hw` rank257 and `vtdec` rank128, both applemedia1.28.3 with P010 output. Expected ordinary hardware-first selection is `vtdec_hw`, with `vtdec` a candidate; this is **not observation of the decoder instance in the running receive graph**. Capability admission separately probes only vtdec_hw. No decoder session was opened by this audit.
- Raw policy is explicitly `video/x-raw,format=P010_10LE`, max1920×1080 and admitted profile-dependent FPS ceiling. Color adapter admits limited BT709 SDR. Video raw queue is3 buffers, leaky downstream, no byte/time limit; appsink is sync/async=true, max3/drop=true. `video_sample` maps P010 and calls `obs_source_output_video2`.
- `timestamp()` (`pixelview-whep.c:191–200`) converts segment PTS to running time plus shared pipeline base, fallback monotonic now if invalid. Both OBS audio/video use this same mapping: no Main10-specific guessed cadence/PTS rewrite here. OBS then has its own async-frame timing and dynamically increasing audio buffering; shared source timestamps do not eliminate downstream OBS/card timing.
- `video_sample:263–299`: once a source has created its native-preview worker, **ordinary Main/Main10 generations continue using it**. A single pending raw sample is replaced by latest; generation/clear ordering is protected, original P010/PTS retained. This history-dependent dispatch survives disconnect until source destruction, and is more than an otherwise transparent appsink adapter. The existing regression exercises this explicitly.
- Audio graph: raw queue200ms → audioconvert/audioresample → F32LE stereo48k → tee. Early native branch: queue200ms/max10 → appsink sync/async=false,max3,drop=false. OBS/rendered branch: leaky queue2s/1MiB/max100 → clocked appsink sync/async=true,max3/drop=true → `obs_source_output_audio`. Early branch exists for ordinary profiles too, but feeds card PCM only for native route. Rendered feed uses the clocked branch (`:361–403`).

## Main10 DeckLink is rendered, not native422

- `decklink-output-ui/decklink-ui-main.cpp:111–178` chooses native only if `native422_frames>0`; ordinary Main10 uses OBS main rendered texture → BGRA stages → video queue(cache16) → native DeckLink output. SDR output is `bmdFormat8BitBGRA`, not faithful native ten-bit422 (`decklink-device-instance.cpp:654–661`). P010 receive/main texture does not certify ten-bit SDI on this path.
- Main10 does not use `DeckLinkReceive`'s timestamped v210 A/V scheduler or its strict native422 rate/admission rules. That scheduler is activated only by `StartNativeOutput`.
- **Custom plumbing does apply to rendered Main10:** `PrepareReceive` attaches `PV_FEED_RENDERED`, substitutes private media, and supplies source-only PCM, not global OBS mixed audio. `pixelview-whep.c:398–399` applies source mute/gain and float→S16 conversion, copying clocked PCM into a bounded10-packet drop-oldest feed (max5760 frames/packet).
- `DecklinkOutput.cpp:93–100` pumps this PCM from each rendered video callback; `decklink-output-receive.inc:107–145` trims packets before first-video timestamp and calls `WriteAudioSamplesSync` through `WriteAudio`, rather than timestamped native422 scheduling. `decklink-output.cpp:235–237` disables ordinary global audio callbacks for receive. Thus card audio is explicitly coupled to rendered-video delivery cadence by Pixelview code. This is an investigation seam, **not an established glitch cause**.
- Rendered health fails when source stops playing/changes to native422 or video counter freshness exceeds500ms. Native scheduler has separate timestamp/expiry/repeat/drop policy. Both routes retain `max(3,device minimum)` preroll; no limits changed.
- Frontend authorization/control is independent of media PTS:65s heartbeat deadline,23h refresh, bounded retry1s→30s; macOS transport resource lifetime24h. Plugin ends an attempt on bus error/EOS or15s without video. These can stop/reconnect reception but are not AV clock correction.
